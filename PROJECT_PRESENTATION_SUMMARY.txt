OMNI-CAMPUS PROJECT PRESENTATION SUMMARY
Version: 2026-04-10
Project Type: Real-time campus monitoring and face-based attendance intelligence platform

====================================================================
1) EXECUTIVE SUMMARY
====================================================================
Omni-Campus is a full-stack, real-time platform for student presence monitoring across multiple camera sources (laptop webcams, Android IP Webcam, DroidCam, and custom IP streams). It combines edge-side face analysis in the browser with secure backend recognition, temporal stability logic, and live event propagation.

The project has evolved from prototype to production-hardened implementation with:
- live multi-camera processing,
- secure recognition APIs,
- encrypted descriptor storage,
- role-based access control,
- signed payload verification,
- audit logging,
- runtime alerts and metrics,
- and presentation-ready dashboards for operations.

Current delivery status:
- Phase 1: Completed
- Phase 2: Implemented
- Phase 3: Implemented
- Phase 4: Implemented
- Phase 5: Implemented

Storage strategy is SQLite-first for speed of iteration and operational simplicity, with clear triggers defined for later Postgres migration.


====================================================================
2) PROBLEM STATEMENT
====================================================================
Campuses need a low-latency, reliable, and auditable way to:
- identify registered students in near real-time,
- track movement by camera zone,
- reduce duplicate/unstable detections,
- support heterogeneous camera hardware,
- and maintain security/privacy controls.

Traditional attendance tools are either manual, not real-time, or difficult to scale securely.

Omni-Campus addresses this with a modular architecture that separates:
- visual inference,
- identity matching,
- temporal decision stability,
- security verification,
- and operations visibility.


====================================================================
3) HIGH-LEVEL SOLUTION OVERVIEW
====================================================================
Omni-Campus uses a hybrid recognition design:

A) Frontend edge layer (browser)
- Captures video/snapshot frames.
- Runs fast face detection and descriptor extraction using face-api models.
- Sends signed descriptor payloads to backend for robust identity decision.

B) Backend decision layer
- Validates signatures and RBAC.
- Runs descriptor matching via ANN abstraction + strict thresholding.
- Applies temporal stability logic (detecting/locked/switching/lost).
- Emits socket updates to all connected clients.
- Stores recognition events in SQLite.

C) Operations and governance layer
- Health, metrics, alerts, and stats endpoints.
- Structured JSON logs.
- Full audit trail for sensitive actions.
- Encrypted descriptor storage at rest.

5) ARCHITECTURE AND DATA FLOW
====================================================================

5.1 FACE REGISTRATION FLOW
1. User opens registration modal and captures multiple face samples.
2. Frontend extracts descriptors from several capture steps.
3. Descriptor set and quality metadata are sent to backend /api/recognition/enroll.
4. Backend validates descriptor quality gates and stores encrypted descriptor history.
5. Student record is upserted with deduplicated descriptor history.
6. student:update is broadcast to connected clients.


5.2 RECOGNITION FLOW (LIVE)
1. CameraFeed reads frame/snapshot and runs face detection locally.
2. Frontend extracts descriptor and sends signed /api/recognition/match request.
3. Backend verifies signature and role context.
4. Descriptor matching runs through ANN-backed candidate retrieval.
5. Match decision passes through temporal stability engine.
6. On confirmed lock, backend updates student location and emits detection:event.
7. Dashboard, feed, and map update in real time via socket broadcasts.


5.3 CAMERA SOURCE FLOW
- Local webcam sources use direct media streams.
- IP/MJPEG sources use backend proxy routes:
  - /api/proxy/stream
  - /api/proxy/snapshot
  - /api/proxy/test
- Stream proxy forwards upstream content-type to support Android IP Webcam compatibility.

6) MODELS USED (CV, MATCHING, STABILITY)
====================================================================

6.1 PRIMARY CV MODEL FAMILY (FRONTEND)
Library: @vladmandic/face-api
Model assets loaded from: /models

Loaded models:
- ssdMobilenetv1
  - Higher-accuracy face detector, used in fallback/quality-sensitive paths.
- tinyFaceDetector
  - Faster detector for real-time low-latency loops.
- faceLandmark68Net
  - 68-point facial landmark estimation for stable descriptor extraction.
- faceRecognitionNet
  - Face embedding network producing descriptor vectors for identity matching.


6.2 MATCHING MODEL
- FaceMatcher with strict Euclidean distance thresholding.
- Default strict threshold around 0.45 (configurable by environment/profile).
- Multi-template per person matching (descriptor history) for robustness.


6.3 ANN SEARCH MODEL (BACKEND, CUSTOM)
- Coarse-centroid ANN abstraction (annIndex service).
- Strategy:
  - Build per-student centroids.
  - Prefilter likely student candidates.
  - Score templates and aggregate best-per-student.
- Supports exact fallback mode and ANN metrics.


6.4 TEMPORAL STABILITY MODEL (BACKEND, CUSTOM)
- Multi-frame identity confirmation logic.
- States include detecting, confirmed/locked, switching, lost.
- Components:
  - consecutive frame requirements,
  - confidence smoothing,
  - lock windows,
  - switch thresholds,
  - drift and motion penalties/boosts,
  - adaptive threshold behavior for latency conditions.
- Multi-track per-camera support with top-2 stable identities.


6.5 PASSIVE LIVENESS MODEL (BACKEND, CUSTOM HEURISTIC)
- Enabled especially for high-risk camera profiles.
- Uses weighted signals:
  - box motion over time,
  - descriptor drift dynamics,
  - client-side confidence/area signals,
  - sample-count sufficiency.
- Produces accepted/pending/rejected liveness decision and score.


6.6 ADDITIONAL ALGORITHMIC MODELS
- Name similarity dedupe (normalized string + Levenshtein-based similarity).
- Descriptor history deduplication via normalized descriptor keys.
- Camera profile threshold adaptation based on profile and camera label.

7) SECURITY AND TRUST CONTROLS
====================================================================

7.1 RBAC
- Roles: viewer, operator, admin
- Protected operations include:
  - enrollment,
  - delete/clear operations,
  - reindex,
  - camera profile update,
  - audit reads,
  - direct matching operations.


7.2 SIGNED PAYLOAD VERIFICATION
- Signed request validation for recognition and tracking mutation APIs.
- Signed socket payload verification for face:detected events.
- Timestamp age checks prevent replay attacks.


7.3 AUDITABILITY
- Persistent append-only JSONL audit logs.
- In-memory recent audit buffer for quick inspection.
- Records include actor, action, status, target, and signature validity metadata.


7.4 DATA PROTECTION
- Descriptor blobs encrypted at rest (AES-256-GCM).
- Legacy descriptor records are migrated to encrypted format when needed.

- Health and diagnostics endpoints:
  - /health
  - /api/health
  - /api/alerts
  - /api/stats
  - /api/recognition/health
  - /api/recognition/metrics

Resilience patterns:
- Per-camera queue and backpressure control.
- Timeout-wrapped matching calls with safe fallback responses.
- Port fallback startup logic to avoid hard boot failure when a port is occupied.
- Graceful shutdown and process-level exception/rejection handlers.

- Face appears to lock: <= 150 ms

15) SCALING STRATEGY (SQLITE-FIRST TO POSTGRES)
====================================================================

Current approach:
- SQLite is intentionally used in early production/staging for simplicity and speed.

Planned migration trigger conditions:
- >50,000 recognition events/day
- >10 sustained concurrent camera streams with heavy writes
- multi-instance backend write requirements
- advanced analytics/report joins at scale

Migration principle:
- Keep interface boundaries clean so DB swap is low-risk.
